What it is, in plain words

Organisations publish aggregates — "the average salary in this team", "the number of cases in this region", "the total spend by this cohort" — believing a total over many people reveals no one. It does, the moment you publish more than one overlapping total. Release a sum over a group, then a sum over that group plus one new member, and the difference of the two sums is that one member's value. No hacking — just subtraction.

This is the differencing attack. It is the reason official statistics agencies, privacy teams, and federated-analytics systems all need disclosure control — and it is subtle, because each release looks safe on its own. The danger is in the history: which cohorts you have already published.

IsolationGate is the gate that remembers. You give it a quorum k (the smallest group you will ever let be isolable) and the contributor set of each release you want to publish. Before it approves a release, it checks that set against every prior release: if the new set minus a prior one, or a prior minus the new, or their overlap, would leave fewer than k people, it refuses — and names which prior release, and how few people would be exposed. The attack is impossible by construction, not by a reviewer remembering to check. The code a mutation gate proves is the code running under your clicks.

import { init, propose } from './kernel.mjs';

// r.ok === false, r.why === 'refused:difference-isolates …'
//   (the new cohort minus the prior is just {f} — below k)

How it works — traced from a real run

Take the differencing attack preset, k = 3. The history already holds one release over {alice, bob, carol, dave, erin}. Now someone proposes a release over the same five plus frank. Each release passes quorum (5 and 6 are both ≥ 3). But here is what IsolationGate checks — the numbers are the live run.

The gate checks three set operations against every prior release — the difference both ways and the intersection — because each is a way to subtract two totals down to a small group. The mutation gate attacks every edge: it flips < k to <= k, drops the reverse-difference check, lets an empty set through — and each of the 22 rewrites is caught by a test.

White paper — the short version

The problem. An aggregate over a group is assumed to be anonymous. It is not, across releases: publishing a statistic over a cohort and another over an overlapping cohort lets an attacker subtract the two and recover the contribution of the people in the difference. This is the differencing attack, and it is the core problem of statistical disclosure control. Each release looks safe alone; the risk is in the history.

The claim. The decision of whether a release is safe should be a pure, deterministic function of the release's contributor set and the sets of all prior releases, so it can be enforced automatically at the release boundary and proven. IsolationGate refuses a release if, against any prior release, the new-minus-prior set, the prior-minus-new set, or the intersection has a non-empty size below k. These are the three ways two totals can be subtracted to isolate a group. k ≥ 2 is the floor.

Why a mutation gate. Passing tests prove the code works on the cases you thought of. A mutation gate proves the tests work: it rewrites the kernel 22 ways — < k→<= k, a dropped reverse-difference, an empty set admitted — and demands the tests catch every one. 22/22 killed means no mutant of this logic survives the suite.

What it is not — stated plainly. IsolationGate is a membership-set gate: it reasons about who is in each release, not the aggregate values or their noise. It closes the exact-subtraction differencing attack over your release history. It does not add differential-privacy noise, model an attacker who combines released values with external data, or decide your k for you — those are complementary controls. It is the gate that makes the set-differencing attack impossible by construction, to compose with your noise and policy layers.
